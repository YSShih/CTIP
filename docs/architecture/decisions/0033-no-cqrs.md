# ADR 0033 — 不採用 CQRS

- 狀態:accepted(2026-08-30,Phase 23 補記;決策自 v2.0 規格成形時即生效)
- 範圍:[01 §1.5](../../spec/01-architecture.md#15-三模型-vs-兩模型強制分類)、
  [§1.6](../../spec/01-architecture.md#16-repository-分層強制)、
  [§1.7](../../spec/01-architecture.md#17-抽象判準強制);全體 application service

## 背景

CTIP 的讀寫比極不對稱:攝取管線每小時寫入數千筆 IOC,而查詢端(檢索、詳情、統計、
Bloom、STIX 匯出)是主要流量。這正是 CQRS 的教科書適用情境,因此**必須明確記錄「為什麼不用」**,
否則後續每一個 session 都可能重新提案一次。

## 決策

**不採用 CQRS**:不拆讀模型/寫模型、不建 command bus、不做事件溯源、不維護獨立的讀取投影庫。
讀寫都經同一組 application service 與同一組 repository port。

## 理由

1. **抽象判準([01 §1.7](../../spec/01-architecture.md#17-抽象判準強制))**:
   「移除某個抽象之後,程式仍然只有一種可能的實作,就不要加這個抽象。」
   CQRS 的價值來自讀寫**各自獨立擴展**;本系統的讀寫都打同一個 PostgreSQL,
   拆開之後兩邊的實作仍然只有一種。
2. **一致性成本是真的**:最終一致的讀模型會讓「剛提交的 IOC 立刻查得到嗎」變成需要解釋的行為,
   而 §7.9 的再散布過濾與 §7.7 的 TLP 可見度是**安全關鍵**的查詢條件——
   它們若因投影延遲而套用到過期的資料快照,結果是資料外洩,不是體驗問題。
   規格模糊時的優先序把安全性排在可擴充性之前([00 §0.4](../../spec/00-master.md#遇到規格模糊時))。
3. **已有針對性的讀取最佳化,而且不需要 CQRS**:
   - 全文檢索走 Elasticsearch([13 §13.7](../../spec/13-platform-ops.md#137-搜尋-phase-12--m1postgresqlphase-19--m2elasticsearch)),
     這已經是一個獨立的讀取路徑,但它是**降級可回退**的次要索引,不是權威來源
   - Bloom snapshot([11](../../spec/11-sync-bloom.md))本身就是一份預先算好的讀取投影
   - STIX 投影(`stix_objects`)是寫入時同步產生的衍生資料
   換句話說:需要獨立讀模型的三個地方**都已經有了**,而且各自帶著自己的失效與重建規則,
   不需要一個全域的 CQRS 框架把它們統一起來。
4. **兩模型/三模型的分類已經解決了「讀取用不到聚合」的問題**
   ([01 §1.5](../../spec/01-architecture.md#15-三模型-vs-兩模型強制分類)):
   append-only 記錄與衍生投影直接以 JPA entity → DTO 映射,不繞經 domain model。
   CQRS 想解的「讀取被寫入模型拖累」在這裡已經沒有了。

## 後果

- 查詢端與寫入端共用交易邊界([01 §1.10](../../spec/01-architecture.md#110-交易邊界))
- 若日後讀取負載真的需要獨立擴展,擴充點是**既有的 `SearchPort`**
  (換掉實作、加讀取副本),不是引入 command/query 匯流排
- 任何提議引入 CQRS 的變更必須先推翻上面第 2 點(安全關鍵過濾條件的一致性)
